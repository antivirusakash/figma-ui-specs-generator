# Internationalization Rules

> Load when: `i18n`, `locale`, `date`, `time`, `number`, `currency`, `format`

---

## Date & Time Formatting

| Rule | Detail |
|------|--------|
| Use `Intl.DateTimeFormat` | Not hardcoded formats |
| Never hardcode format | No `MM/DD/YYYY` strings |

```tsx
// GOOD
new Intl.DateTimeFormat('en-US', { dateStyle: 'medium' }).format(date)

// BAD
`${date.getMonth()}/${date.getDate()}/${date.getFullYear()}`
```

---

## Number & Currency Formatting

| Rule | Detail |
|------|--------|
| Use `Intl.NumberFormat` | Not hardcoded formats |
| Currency symbols | Via `Intl.NumberFormat` |

```tsx
// GOOD
new Intl.NumberFormat('en-US', { style: 'currency', currency: 'USD' }).format(amount)

// BAD
`$${amount.toFixed(2)}`
```

## Language Detection

| Method | Use |
|--------|-----|
| `Accept-Language` header | Server-side |
| `navigator.languages` | Client-side |
| IP geolocation | **Never** for language |

---

## Current Scope

| Setting | Value |
|---------|-------|
| Language | English only |
| i18n framework | Deferred to future phase |

---

## Hydration Considerations

| Issue | Solution |
|-------|----------|
| Date/time mismatch | Guard against server/client timezone differences |
| Locale mismatch | Ensure consistent locale between server/client |

---

## Violations (Auto-Fail)

```
MM/DD/YYYY            → Use Intl.DateTimeFormat
toFixed(2)            → Use Intl.NumberFormat for currency
${date.getMonth()}    → Use Intl.DateTimeFormat
IP-based language     → Use Accept-Language or navigator.languages
```
